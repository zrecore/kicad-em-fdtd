# Plan: real-time 3D EM wave simulator as a cross-platform KiCAD plugin

Status: **working prototype on macOS** (snapshot -> voxelizer -> CPU and Vulkan solver with CPML and lumped ports -> S11 and an animated field view in a standalone window; KiCAD plugin entry point written, untested inside KiCAD). Plan restarted 2026-11-19 and updated through the same session with measurements, findings from the pg-strom and mongo sessions and probes of the Windows box. Scope is this repository only. The sections below were written as a plan; "Measured so far" and "Next steps" record what has been built.
Example board: the user's own KiCAD design in `../bomu-hardware/bomu`, used as read-only test input. By the user's instruction nothing from that repository is copied or committed here.

## Focus
**Make it work on this Mac first** (Apple M1 Pro, MoltenVK, local KiCAD). Windows and Linux support, the Windows eGPU, CI, packaging, signing and PCM distribution come later. Keep the code portable (no Apple-only shortcuts), but do not build, test or tune for other platforms yet.

## Goal
Simulate electromagnetic waves on a KiCAD board in 3D on the GPU and show the fields live in 3D, packaged as a KiCAD plugin that runs on macOS, Windows and Linux.
**First target:** the 2.4 GHz (WiFi band) antenna path on the example board.

## Decisions so far
- Solver method: **FDTD** (finite-difference time-domain, Maxwell's equations stepped in time on a 3D grid).
- Compute and graphics API: **Vulkan 1.2 baseline** (MoltenVK on macOS). Not CUDA, so that Apple, AMD, Intel and NVIDIA GPUs all work.
- Cross-platform is the eventual goal (macOS, Windows, Linux), but macOS comes first.
- License: **MIT** (decided 2026-11-19). See Licensing below for dependencies, the clean-room rule and open patent items.
- Plugin type: **KiCAD IPC API plugin**. Legacy SWIG `pcbnew` plugins are deprecated; do not use them.

## Product requirement: works on the user's own design
The plugin is a tool for anyone to run on **their own board in KiCAD**. The example board and the W3008 reference board are only test cases; nothing in the plugin or solver may be specific to them (no hard-coded part, net, layer, board size or antenna).
- **Input comes from the open board:** outline, stackup (layers, thicknesses, er, tan delta, copper weight as set in KiCAD's board setup), copper (tracks, pads, vias, filled zones), and footprint positions, all read through the IPC API. When the stackup lacks material values, use documented defaults and show the user what was assumed.
- **User choices in the UI, with sensible defaults:** the frequency range; the excitation (pick a port as two pads or pad and net, with a reference impedance, or a plane-wave or dipole source); the region of interest (crop to a box or selected footprints plus margin, since simulating a whole large board at fine resolution does not fit in memory); which components count as metal or dielectric bodies; boundary distance.
- **The user selects which components take part, separately for the model and for the view.** From the footprints, nets and layers of their own board the user chooses (a) what is in the electromagnetic model and (b) what is drawn in the 3D view. These are two independent selections, so a part can be modelled but hidden, or shown for context but left out of the model. Each included component gets a treatment the user can override: metal body, dielectric block, lumped element (a resistor, inductor or capacitor with its value), or ignored; defaults depend on the footprint type, and a part without a 3D model falls back to its courtyard box with a warning. Selections can start from what is selected in the PCB editor, from a list with filters (by reference, value, net, layer, region), or from presets such as "everything within the region of interest". The choice is stored in a sidecar file next to the board, never in the KiCAD design files, and the run summary lists what was included and how. Whether `kipy` 0.8.0 exposes the editor's current selection is unverified and part of the probe step.
- **Resource limits are reported, not hidden:** estimate cells and memory from the chosen region and resolution before running; coarsen automatically or tell the user how to shrink the region; refuse with a clear message rather than crash.
- **Unsupported features are detected and named** (for example blind and buried vias, curved or complex zones, component bodies without 3D models), with the simplification used. Nothing is silently dropped.
- **Results go back to the user:** viewer for fields, S-parameters exported as Touchstone, and a summary of the assumptions used so results are reproducible. Suggestions are shown, never applied to the design automatically; the plugin never modifies the board.
- **Version tolerance:** target the KiCAD 10 IPC API through `kipy`, report the version in use, and fail with a clear message on an unsupported version.
- **Testing consequence:** besides the W3008 board and the user's example board, add at least one board of a different shape, layer count and part (for example a plain 2-layer board with a microstrip line), so we do not tune the pipeline to one design.

## Defaults and editable attributes
Every physical attribute the model needs has a default and the user can change it. Nothing is hard-coded in the solver or the plugin.
- **One data file holds the defaults:** `data/fab_profiles.json` (materials, and fabrication profiles with their limits). The solver app, the plugin and the board generators read it; no second copy in code. Each value records its `source`, and values no fab publishes are marked `assumed`.
- **Built-in profiles (fab pages read 2026-11-19 and 2026-11-20, linked in the file), one per copper-layer count, all ENIG FR4-class:** OSH Park 2-layer (one 60 mil 175Tg FR4 core, Dk 4.5 at 10 MHz), 4-layer (FR408HR: 7.87 mil prepreg, 39 mil core, 7.87 mil prepreg, Dk 3.61 at 1 GHz) and 6-layer (FR408HR: 4.36 mil 106 prepreg, 4 mil 2113 core, 36.44 mil core, 4 mil 2113 core, 4.36 mil 106 prepreg; Dk 3.23 to 3.66 and Df 0.009 to 0.011 at 1 GHz where published); PCBWay 2-layer (a single 1.53 mm core, derived: PCBWay publishes no 2-layer stackup) and 4-layer (entry 1 of its stackup table: 1.6 mm, 7628 prepreg 0.1855 mm Dk 4.74, core 1.03 mm Dk 4.6, no frequency stated); and **`common_denominator`**, the default for the reference boards. Laminate values come from the datasheets OSH Park links (read 2026-11-20): Kingboard KB-6167F (OSH Park 2-layer: Dk 4.6, Df 0.016 at 1 GHz; the OSH Park page itself says Dk 4.5 at 10 MHz) and Isola FR408HR (Dk 3.69, Df 0.0091 at 1 GHz, used for the cores whose Dk the page omits and for the prepreg Df). Still assumed and named in each layer's `assumed` list: the FR408HR prepreg loss tangent (laminate value used), and all PCBWay values that are not Dk (Df 0.016, the KB-6167F figure; the 2-layer thickness and Dk). PCBWay's page counts 112 four-layer stackups of 298 but the 6-layer tables could not be read (its 6-layer example is an image), so there is no PCBWay 6-layer profile; PCBWay publishes no 2-layer stackup, no Df and no Dk frequency, and lists ENIG with no layer-count restriction. Fab limits (track, space, drill, ring) stay in each profile.
- **Assumed material values:** FR-4 er 4.5 and tan delta 0.02 (neither fab states them; FR408 is given the same until a datasheet figure is entered), solder mask er 3.5 and 0.01 mm thick, bulk copper conductivity 5.8e7 S/m (real PCB copper is lower), copper-to-board-edge clearance 0.3 mm, absorbing-boundary distance a quarter wavelength (to be confirmed by convergence tests). These are labelled assumed in the file and in the run summary.
- **Precedence (highest wins):** a value the user sets in the plugin dialog, then a value in the board's own KiCAD stackup (read through the API, used when it carries a real number), then the selected fabrication profile, then the built-in default. The user's overrides are stored in the sidecar file next to the board (never in the KiCAD design files), so they travel with the project.
- **What the user can edit (built 2026-11-20, Settings, group PCB):** "PCB stackup" (the board's own stackup, the default, or any fab profile) and, for up to 7 dielectric layers counted from the top, thickness, permittivity and loss tangent (0 keeps the board's value), plus outer and inner copper thickness (recorded only: copper is a zero-thickness sheet in the model). A profile starts the values; typing one overrides it. A profile for another copper-layer count is refused with a note, not applied silently; typed values still apply. Every change is listed in the run notes with its origin (your value, profile, assumed). Still to do from the list below: solder mask, finish, board-edge clearance and the layer materials by name, and a per-layer table in place of the slots. Original list: the profile choice; per-layer thickness, copper weight, material name, er, tan delta and conductivity; solder mask; finish; the board edge clearance; the boundary distance; the grid resolution rules. Edits apply to the run only, and the run summary lists every value used and where it came from (user, board, profile or default).
- **Why a fab profile matters to the simulation:** the stackup and copper weight set the dielectric heights and conductor thickness in the model, and the fab limits tell the voxelizer which features are real (for example a gap below the profile's minimum is flagged), so results match the board the user would actually order.
- **Open items:** the er and tan delta values to use for a given fab's FR-4 and FR408 (get the laminate datasheets and add them with sources), and whether to add more fab profiles (for example JLCPCB) later.

## Architecture
```
KiCAD PCB editor -> thin Python IPC plugin (kipy) -> board snapshot -> native C++/Vulkan app
                                                     (voxelizer -> FDTD compute (SPIR-V) -> 3D viewer GLFW + ImGui)
                                                     backends: Vulkan GPU | CPU fallback
```
- The plugin is a separate process (`plugin.json`, toolbar action) that exports a snapshot of the board.
- The solver and viewer is a separate native app with its own window (a plugin cannot draw inside KiCAD's window). It must also run standalone without KiCAD.
- One snapshot format (for example JSON plus a binary blob) is shared by the plugin and the C++ app.
- A CPU backend sits behind the same interface as the GPU one, for CI, machines without a GPU, and cross-checking GPU results.
- Shaders are GLSL compiled to SPIR-V at build time with `glslc`.
- Build: CMake and C++20. Dependencies (GLFW, Dear ImGui, VMA, volk) come from vcpkg or FetchContent.

## FDTD design
- Yee grid [1]: E and H update kernels (3D dispatch, shared-memory tiling), absorbing boundaries (CPML [4][5]), a lumped port or soft source (3D lumped-element formulation [7]; the 1992 paper [6] is 2D), running DFT accumulators at chosen frequencies.
  A Gaussian pulse drive plus a DFT of port voltage and current gives S11 over the whole band from one run.
- **Graded (non-uniform) grid:** the grid is made of small boxes (cells). A uniform 0.1 mm grid over a whole board is about 160M cells (about 4 GB in fp32, about 12 steps/s): too slow.
  A uniform 0.25 mm grid is about 10M cells (roughly 200 steps/s) but is too coarse for thin (about 0.1 mm) board layers. A graded grid uses fine cells where detail matters (through the
  stackup in z, and near the antenna in xy, about 0.1 to 0.2 mm) and grows to about 1 mm toward the boundary. Thin copper is modelled as PEC or as thin conducting sheets with a subcell model [8].
  Timing figures are estimates from memory bandwidth and must be measured.
  Accuracy: on a non-uniform Yee grid the local truncation error drops to first order where neighbouring cell sizes differ, but convergence analysis exists for the scheme [10]. We have NOT verified a numeric grading-ratio limit from the literature (only the paper's bibliographic record was checked, not its contents). Rule until then: grade smoothly (neighbouring cells differ by a small factor), never jump in size at a material interface, and decide the ratio from our own convergence tests (halve the grid and compare S11 and resonance).
- **Time step (correction):** the explicit scheme is stable only if the time step is below the 3D Courant limit, dt <= 1 / (c * sqrt(1/dx^2 + 1/dy^2 + 1/dz^2)) [2][3][15], and with a graded grid ONE global step is set by the smallest cell. So fine z cells through the stackup slow every cell in the domain, not just the thin region. Computed here at 2.44 GHz (period 410 ps): uniform 0.1 mm cells give dt about 0.19 ps (about 2100 steps per cycle); 0.1 mm in xy with 0.05 mm in z gives dt about 0.14 ps (about 3000 steps per cycle); uniform 0.25 mm gives dt about 0.48 ps (about 850 steps per cycle). Total cost is cells times steps, so the earlier steps-per-second estimates understate the run time. Local time stepping or subgridding could remove this penalty but is a research item whose stability is not verified here.
- Real-time expectation: at 2.4 GHz a wave period is about 2000 to 3000 time steps (see the time-step item above), so a continuous-wave view runs well below wall-clock speed. S11 ring-down needs tens of thousands of steps (50 000 steps is about 7 ns of simulated time at dt 0.14 ps), which takes seconds to minutes of GPU time depending on the measured step rate.
- Batch many time steps per command-buffer submission, keep fields in GPU memory, and read back only probes and accumulators every N steps.
- Sub-cell features (for example a 0.07 mm gap) need a conformal or subcell treatment; see the patent item in Licensing before choosing one [9]. fp32 fields are fine; DFT accumulation needs compensated (Kahan) summation [14] or fp64 on the CPU.
- Stackup and material defaults come from `data/fab_profiles.json` and are user-editable (see Defaults and editable attributes). Material parameters missing from datasheets (for example ceramic permittivity) make absolute resonance uncertain without a measurement. The viewer is for field patterns and trends.

## Performance strategy
Run time = cells x steps / cell-updates per second. FDTD is bandwidth-bound: the update does 7 floating point operations per field component against 24 bytes moved, far below a GPU's compute-to-bandwidth ratio [16], so memory traffic sets the speed and the roofline view applies [13].

**Source-backed and derived figures**
- Floor per cell-step: 6 field components each read once and written once in fp32 is 12 x 4 = 48 bytes (derived; ignores material coefficients and halo re-reads).
- Measured elsewhere: on a GTX 1080 Ti, gprMax's free-space cubic models reached up to 3405 Mcells/s [16] at a measured 360 GB/s, which is about 106 bytes per cell-step effective (derived from those two numbers). Free-space cubes have trivial materials, so a board with many materials will be slower.
- Updated estimate from the measured 182 GB/s copy bandwidth (kernels typically reach 85 to 90 % of it): about 155 to 165 GB/s, so roughly 1.5 Gcells/s at 106 bytes per cell-step, up to about 3.4 Gcells/s at the 48-byte floor. A 10M-cell grid would then run about 150 to 340 steps/s, and 50 000 steps would take about 2.5 to 5.5 minutes. Still an estimate until the FDTD kernel is benchmarked (step 3).
- Budget placeholder: set a target (steps/s for a given cell count on the M1 Pro) after the step-2 benchmark, then track it so a regression is visible.

**Levers, in priority order**
1. Fewer cells: region-of-interest crop, graded grid, automatic coarsening, memory estimate before the run (see Product requirement).
2. Fewer steps: one broadband pulse gives S11 over the band; stop when the field energy has decayed; do not over-resolve thin layers because the smallest cell sets the time step (see Time step).
3. Fewer bytes per cell: compact material indices instead of per-cell coefficients; fp32 fields; later fp16 storage and temporal blocking [12] only if measurements justify it.
4. Keep the GPU fed: fields stay in GPU memory, short submits (watchdog), no per-step host work; absorbing boundary only on boundary slabs.
5. Display cost: the multi-frequency DFT accumulators at display resolution add about 1 % of solver traffic per field component at 10M cells and S = 100 (derived, see Viewer design: N = 15, 128^3), growing with display voxels over solver cells; the per-frame reconstruction and ray march are separate render costs. N, the number of components and the display grid are tunables.
6. Startup: several small kernels, a persistent pipeline cache, parallel CPU voxelization.
7. Measure with timestamp queries, warm runs, medians, against the measured copy bandwidth, under the GPU lock.

## Parallelism in the GPU design
FDTD is data-parallel: within one time step every cell's update depends only on its neighbours' values from the previous half-step. The cost is dominated by memory traffic, not arithmetic, so the design aims to keep every GPU core busy and every byte loaded once.
- **One invocation per cell (or small cell group).** The E update and the H update are two 3D dispatches per step. Between them is a barrier, since H needs the finished E and the reverse. Nothing else in the step needs ordering.
- **Memory layout for bandwidth.** Store each field component (Ex, Ey, Ez, Hx, Hy, Hz) as its own array (structure of arrays) with x fastest, so neighbouring invocations read neighbouring addresses (coalesced). Material coefficients are stored per cell in compact form (a material index plus a small table) rather than six floats per cell.
- **Workgroup tiling (corrected after reading [11]).** The established GPU method is not a 3D tile in shared memory. Each workgroup loads a 2D tile plus a one-cell halo of the x-y plane into shared memory and marches along z, the slowest axis, keeping the neighbouring slices in registers [11]. Read redundancy is (n*m + k*n + k*m) / (n*m) with k the stencil width; the Yee update reads only +-1 cell, so k = 2 and a 16 x 16 tile gives at most 1.25 and a 32 x 32 tile 1.125 (derived here; the staggered stencil may do better). Tile shape is a specialization constant chosen per device. **But start simple:** the gprMax GPU engine uses plain 1D-indexed, coalesced kernels with no tiling and reports near-peak bandwidth with similar performance to tiled designs [16]. So version 1 is the simple coalesced kernel, and tiling is added only if the benchmark shows it helps on the M1.
- **Fuse where possible.** Apply the source term and the PEC and conductivity-sheet corrections inside the update kernel instead of separate dispatches. Absorbing boundary (CPML) work runs only on the boundary slabs, in its own small dispatches, so the interior stays a simple stencil.
- **Cheap reductions.** DFT accumulators and probes use subgroup operations and a per-workgroup partial sum, then one small final pass, instead of atomics on every cell.
- **Many steps per submission.** Record N time steps into one command buffer, with barriers only between E and H passes, so the CPU is never in the per-step loop. Readback is limited to probes and accumulators every N steps.
- **Compute and rendering.** The viewer does not read the solver arrays directly; see Viewer design. MoltenVK exposes four queue families (probe below), but whether the Apple GPU runs work from them concurrently is unmeasured, so do not rely on async compute until measured.
- **Graded grid and parallelism.** Keep the grid structured (a regular index space with per-axis cell sizes), so the kernels stay branch-free and coalesced. Cell sizes are 1D lookup tables per axis.
- **CPU backend parallelism.** Same update structure, split across threads by z-slabs, with vectorized inner loops over x. It doubles as the correctness reference.
- **Later options (only if measurements justify them):** fp16 field storage to halve bandwidth, temporal blocking (several steps per tile) [12], splitting the domain across two GPUs with halo exchange, and a CUDA backend.
- **Measure first, against a measured ceiling.** gprMax reached about 320 GB/s of the 360 GB/s that the BabelStream copy benchmark measured on a GTX 1080 Ti (about 89 %), and BabelStream itself reached only 66 to 75 % of the theoretical peak on the NVIDIA cards tested [16]. So our denominator is a copy-kernel bandwidth measured on this machine, not the spec-sheet number, and the target is about 85 to 90 % of it.

## Viewer design
**Display path (decision).** The solver's field arrays and the viewer's data are separate. A compute pass writes the quantity to display into a separate 3D image: reconstructed each animation frame from the N-frequency phasor accumulators (see Animation), or, for a live preview, resampled every M steps (R8_UNORM or R16_SFLOAT, normalised), at a size capped for display (proposal: at most 256 voxels per axis by default, about 17 MB at 8 bits; larger on request). The viewer ray-marches that image in a fragment shader over a cube proxy [19][18] and draws the board geometry (outline, copper polygons, component boxes) as ordinary triangles. This replaces "the viewer reads the solver buffers".
- **Ray marching:** accumulate colour and opacity front to back along each ray, stop early once the opacity is high enough, and skip empty space using a coarse min/max grid [18]. Krüger and Westermann implemented this with multiple passes and the early depth test on 2003 DirectX 9 hardware; modern shaders can loop and exit early inside one shader, so the techniques carry over but the mechanism does not [18]. The field is concentrated near the antenna and tiny elsewhere, so a log transfer function and a user threshold matter more than the marcher's speed. Slice planes are a cheap second view.
- **Graded grid:** resample to a uniform display volume inside the snapshot pass, fetching the solver arrays through per-axis coordinate tables. Why: the ray marcher stays simple and hardware trilinear filtering works, and the cost is one pass per M steps. The alternative, marching in the non-uniform index space with per-axis lookups on every sample of every pixel every frame, costs more.
- **Synchronisation:** two display images. The solver writes one while the viewer reads the other; swap at an M boundary with a single compute-to-fragment barrier. All four MoltenVK queue families here support graphics, compute and transfer, so one queue family is enough and no ownership transfer is needed.
- **Frame budget:** a long solver submit also starves the swapchain. The "tens of ms" submit rule from the watchdog lessons is also the frame budget: submits are sized so a display frame fits between them (assumption: about 8 ms; measure).
- **Snapshot cadence M** is a user-visible performance knob (smooth view versus solver speed), exposed with a default.

**Animation (requirement: the 3D view is an animation of the waves).** The render side is settled above. The open question is how to represent time. Candidates, compared on four axes: (a) extra solver traffic, (b) display-data memory, (c) per-frame cost, (d) temporal fidelity. Reference case for the numbers: 10M solver cells, a 128^3 display grid (2.1M voxels, which is 0.16 mm voxels over a 20 mm region of interest), sampling every S = 100 solver steps (3000 steps per cycle, dt about 0.14 ps), N = 15 frequencies. All figures are derived here, not measured.

| **3. Frame store** | about 0.1 % (one 12 B read per voxel per frame) | 2.1 MB per frame at 128^3, 8 bit: 2.1 GB for 1000 frames; 17 GB at 256^3 | read one frame | transient, but time resolution fixed at the recording interval M; scrub only over recorded frames |
| Live (no storage) | none | none | none | 2 to 6 frames per second at the estimated 120 to 300 steps/s, so not smooth |

**Decision (proposed): representation 2 as the single mechanism, with representation 1 as its N = 1 case and representation 3 only as a live preview.** The same DFT accumulator path then serves S11, steady-state animation and transient playback. The three checks the choice depends on:
1. **N (number of frequencies):** a signal confined to a window T is fully described by its DFT at spacing df = 1/T. For T = 50 000 steps x 0.14 ps = 7 ns the spacing is about 143 MHz; a 2 GHz-wide excitation band (for example 1.5 to 3.5 GHz) needs N about 14, so use N = 15 to 20. This needs the excitation to be band limited and the fields to have decayed by the end of the run (otherwise the animation wraps around at T); an antenna with a narrow resonance rings long, so the ring-down time sets T.
2. **Memory:** accumulators live at display resolution, not solver resolution. At 128^3 with N = 15 they are 252 MB per component in fp32 (fp32 because summing thousands of samples in fp16 loses precision, the reason compensated or wide accumulation is already in the plan). At 256^3 they would be 2 GB per component, and the traffic below would be about 8 times higher, so the display grid is capped at about 128^3, which the region-of-interest crop makes adequate.
3. **Traffic:** per sample per display voxel per component: one 4 B read of the field plus a read and write of 15 complex fp32 accumulators (240 B) = 244 B. Against S x 48 B x cells of solver traffic this is 1.1 % per component at 10M cells and S = 100. It scales with display voxels over solver cells: for a 2M-cell solver it would be about 5 % per component, so the number of components and N are exposed as knobs. The sampling interval S x dt must stay below half the period of the highest frequency present (about 700 steps for 5 GHz content at dt 0.14 ps); desampling the solver's oversampled time series this way is standard [22].
Both are under the 10 to 15 % threshold, so the single-mechanism design stands. If a run ends with a lower cell count and more components, the plan falls back to representation 1 plus 3.

The sources behind this: running-DFT field conversion for multiple frequencies from one pulsed run, with storage of 2 x points x parameters x frequencies values and a cost of one complex multiplication per time step, point, parameter and frequency, is the standard FDTD approach and desampling is a known saving [22][23]. An alternative that solves N equations for N unknowns from 2N time samples (NENU) needs a source built from a sum of sine waves and can be ill-conditioned, so it does not fit a pulse excitation [22]. The survey of time-varying volume rendering reviews the same trade-off (store or compress many time steps, or reduce the data) and treats time separately from space as the usual choice when temporal and spatial coherence differ [20]; compressed time-varying approaches (palette and transform coding, time-space partitioning trees) exist for very large simulations [24][25][26] and are not needed at our sizes.

- **Reconstruction runs in a compute pass per animation frame into the display image, not per ray sample in the fragment shader:** millions of voxels x 15 multiply-adds per frame, against billions of ray samples. The ray marcher then sees an ordinary scalar volume, as designed above.
- **Per-frame render cost (formula):** texture fetches per frame = pixels x samples per ray x rho, where samples per ray = volume depth in voxels x oversampling and rho is the fraction left after early termination and empty-space skipping [18]. At 1920 x 1080 (2.07M pixels), 128 voxels deep, oversampling 3 (384 samples) and rho = 1 this is about 0.8 billion fetches per frame, 48 billion per second at 60 fps. The M1 Pro's 3D-texture fetch rate has not been measured: it is a step-6 probe, and the numbers above are an upper bound. Mitigations in priority order: early ray termination and empty-space skipping [18]; pre-integrated classification, which gets equal image quality with fewer samples but needs its lookup table rebuilt when the colour map changes [21]; reduced resolution and fewer samples while the camera moves; slice planes.
- **Slice planes first.** A 2D slice costs one fetch per pixel (2M per frame), so it is the cheapest view and the first thing step 6 builds, before the ray-marched volume.
- **Signed field:** a wave only looks like a wave if the sign is kept, so show a signed component (diverging colour map) or the instantaneous real field. Time-averaged |E| hides the propagation and is for the static pattern only. Transfer-function design is surveyed in [27].
- **Controls:** play and pause, loop, playback speed against physical time (picoseconds, for example "1 s = 20 ps"), a time or phase slider, frequency selection, field component, colour map, threshold, slice planes, the component selection described under Product requirement.
- **Render rate is independent of solver rate:** the viewer renders at the display refresh rate; provide a resolution scale while the camera moves.
- **Consequence for the plan:** the solver carries a multi-frequency DFT accumulator at display resolution from the start (a knob for N, components and region), and the viewer needs only the reconstruction pass and the ray marcher.

**Probed on this Mac (2026-11-19, `vulkaninfo` under the GPU lock):** four queue families, each graphics + compute + transfer with 1 queue, 64 timestamp bits and present support; `VK_EXT_metal_surface` and `VK_KHR_surface` available; R8_UNORM, R16_SFLOAT and R32_SFLOAT all support sampled image, storage image and linear filtering with optimal tiling; `maxImageDimension3D` is 2048; shared memory per workgroup 32 KB; subgroup size 32.
**Still to probe:** presentation through GLFW (not installed; its MoltenVK surface path is unverified), whether work on different queue families actually overlaps on this GPU, the cost of writing a 3D storage image versus a buffer, and the image layout transitions needed for storage write then sampled read.

## Lessons from other GPU projects on these machines
Reported by the pg-strom session (Vulkan GPU offload) and the mongo session (Vulkan mesh work), both on the same M1 Mac and Windows RTX 4060 Ti. They come from those projects' experience and are unverified for this one. Details: `/Volumes/CrucialX9/Projects/mongo/poc/gpu/extension/PLAN.md` and `poc/gpu/README.md` (branch `vulkan-gpu`), read-only references.
- **Watchdog and the viewer:** a long-running dispatch can trigger `VK_ERROR_DEVICE_LOST` through the macOS GPU watchdog and also freezes UI interactivity. Keep each submit short (tens of ms) and split a batch of time steps into several submits. This directly limits the "many steps per submission" rule above, and matters because the viewer shares the GPU.
- **Shader compile time:** one huge SPIR-V kernel can take minutes on Metal. Prefer several small kernels (E update, H update, CPML, DFT) over one ubershader. Persist a `VkPipelineCache` and cache SPIR-V by source hash.
- **Feature tiers:** M1 has no fp64 and no 64-bit buffer atomics. Do not depend on them; query caps with small probe kernels as well as feature flags. Enable storage8/16, int64 and subgroup ops explicitly when needed. Our fp32 plan with Kahan summation or CPU fp64 fits this.
- **Differential testing:** compare GPU against the CPU reference on small grids. It caught an NVIDIA driver bug in 64-bit signed remainder, and is the main correctness tool here too.
- **Process model:** Metal's shader compiler cannot run in a forked process. Do not `fork()` after Vulkan initialization; spawn a separate process instead (relevant to the plugin launching the solver app).
- **Benchmarking:** wall time from submit to fence is CPU-side, so use timestamp queries for device time. Pipeline creation costs 400 to 700 ms on first use: warm up, report best of 3, and measure on an otherwise idle machine. Unified memory on the M1 gave about 31 GB/s effective in their workload (data-dependent), so measure our own bandwidth first. Concurrency knobs (queue depth, chunk size) gave 8% or less; kernel specialization mattered more.
- **GPU sharing and locking (Mac):** never run two GPU programs at once on the M1, and run tests at `nice -n 10`. Existing wrappers (verified present): `/Volumes/CrucialX9/Projects/pg-strom/test/gpuserv/gpu_lock.sh` and `/Volumes/CrucialX9/Projects/mongo/poc/gpu/tools/with_gpu_lock.sh`. Read them before use; do not copy them in.
- **GPU sharing and locking (Windows, later):** the FIFO lock is `/Volumes/CrucialX9/Projects/pg-strom/test/gpuserv/win_gpu_lock.sh` (`hold <label> <min>` in the background and wait for the line HOLDING, `status`, `release <label>`). Only the lock holder asks the Windows agents to run GPU programs, one at a time. Windows GPU runs need this project's user's approval; peer sessions cannot give it.
- **Metal compiler bug:** spec-constant-sized arrays can be miscompiled. Use a fixed maximum array size and test every parameter dimension (loop bounds, sizes), not just one. This matters because the plan tunes tile size through specialization constants.
- **Floating point:** GPU compilers may fuse multiply-adds. Keep a CPU oracle and test it with `-ffp-contract=off` and `=fast`; compare results on every device.
- **Measure warm, not cold:** the first run includes device and pipeline creation (about 40 ms on the M1, 100+ ms on Windows). Report the second run or medians of 5, and measure the submit floor by dispatching one workgroup.
- **GPU is not automatically faster than the 8-core M1 CPU** (unified memory): copies and data movement around the kernel can cost more than the kernel. For FDTD the fields stay on the GPU, but budget the viewer snapshot and probe readbacks up front.
- **Toolchain:** `glslc -O` vs `-O0` made no difference for them. Use the Vulkan SDK's `glslc` and `volk`, and set `VK_ICD_FILENAMES` to the SDK's `MoltenVK_icd.json` if the loader does not find MoltenVK. SPIR-V checked in as a generated header is an option.
- **Device robustness:** use a finite fence wait, never free buffers after a failed or timed-out wait (work may still be running), and treat a failed submit as poisoning the context.
- **Windows box (later):** native Vulkan through NVIDIA's driver works for compute; check `nvidia-smi` first (the eGPU dropped out once). Mesa Dozen under WSL is non-conformant, so its results are not representative. The box has had two blue screens (not caused by GPU runs; one involved exFAT on a USB SSD), so keep irreplaceable data off that drive. For Windows builds, the mongo project cross-builds with mingw in a Debian container and delivers over the SMB share the user mounts on the Mac (only the user can enter the password; verify sha256 on both sides). Here the simpler route is probably building natively on the box with Visual Studio (see Hardware), to be decided when Windows work starts.
- **WSL2:** Mesa `dzn` lacks 8-bit storage and 64-bit atomics, and there is no NVIDIA Vulkan driver under WSL. Use lavapipe (CPU Vulkan) on Linux for host-code and CI checks, and Windows-native for the NVIDIA GPU.
- **Housekeeping:** keep scripts in the repo, not `/tmp`; keep big data off the internal disk. macOS has BSD `sed`, `awk` and `wc`, `echo -n` is not portable, and the system GNU make is 3.81.

- 2026-11-19, `build/hello_compute` (cold, single run, so not a benchmark): Apple M1 Pro, vendor 0x106b, Vulkan 1.2, 17.2 GB reported as device-local (unified memory), compute queue family 0 of 4, 64 timestamp bits. 1M-element dispatch passed with 0 mismatches; wall 2.6 ms, GPU 0.5 ms.
- CMake found the Homebrew Vulkan loader (`/opt/homebrew/lib/libvulkan.dylib`, 1.4.363) and it found MoltenVK without `VK_ICD_FILENAMES`. `VULKAN_SDK` is unset in the shell, so the SDK at `~/VulkanSDK/1.3.283.0` is not what the build uses; `glslc` came from `/usr/local/bin`.
- 2026-11-19, `bench` (release, warm, medians of 9 and 21, under the GPU lock): **copy bandwidth 182 GB/s** (512 MiB buffers, read + write, 3 passes per submit; about 91 % of the 200 GB/s spec) and **submit-to-fence floor 0.28 ms** for a one-workgroup dispatch. A 3-pass copy submit takes about 18 ms wall. Memory type was host-visible and coherent, which on this unified-memory machine is the real bandwidth (flags are recorded in `out/bench.json`). The GPU test scenario passed with the validation layer confirmed active and zero validation errors.
- 2026-11-19, **IPC probe** (`plugin/probe/dump_board.py`, read-only, run against a copy of the W3008 test board in pcbnew 10.0.7): `kipy` 0.8.0 connects to KiCAD 10.0.7 over the default socket after launching `pcbnew` with the board. Exposed and working: version, board name, copper layer count, net list, footprints (position, reference and value fields, a `definition` with a `models` list that was empty for our model-less footprint), pads (number, position, net, padstack, `get_pad_shapes_as_polygons`), tracks, vias (position, diameter, drill, net), zones, the current selection (`get_selection`, readable, empty here), item bounding boxes, and the stackup (`get_stackup`: layers with type and thickness in nm, `edge`, `finish`, `impedance`; dielectric layers carry sub-layers that hold the material values, whose attribute names still need to be confirmed). Zone `filled_polygons` came back empty because the zones had not been filled in that session; `refill_zones` exists but changes the open board in memory, so it must be explicit and never saved. Not yet confirmed: whether 3D model references come back for a footprint that has one, and the dielectric sub-layer attribute names.
- 2026-11-19, **first GPU FDTD kernel** (`shaders/fdtd_step.comp`, simple coalesced version, no tiling, per-node coefficient arrays): **1845 Mcells/s** on a 160^3 PEC cavity, 22 ms per 10-step submit. That is about 99 bytes of traffic per cell-step if the kernel sits at the measured 182 GB/s copy bandwidth, close to the 106 bytes derived from gprMax and consistent with being bandwidth-bound. The kernel moves roughly 72 bytes per cell-step (6 fields read and written plus 6 coefficient floats), so the main lever is replacing the six per-node coefficient floats with a one-byte material index and a table (about 25 % less traffic), before any tiling. A 10M-cell grid would run about 185 steps/s today (50 000 steps in about 4.5 minutes). The GPU matches the CPU reference within 1e-4 of the peak after 200 steps on a uniform and on a graded grid (float rounding only), with zero validation errors.
- 2026-11-19, **material palette** (one packed word per node holding three 1-byte palette indices into a (ca, cb) table, replacing six coefficient floats): **2290 Mcells/s** on the same 160^3 case (+24 %, 17.9 ms per 10-step submit), GPU still within 1e-4 of the CPU reference on a uniform grid, a graded grid and a cavity with dielectric, lossy and PEC regions. The palette is limited to 256 distinct edge materials; the host throws if a model exceeds it.
- 2026-11-19, **CPML and lumped port** (CPU reference and GPU): CPML (kappa = 1, order 3, target 1e-6 reflection, 8 layers) leaves 1.5e-10 of the PEC-box energy on a uniform grid and 7e-11 on a 3 %-graded grid after 600 steps (test threshold 1e-6). A 50 ohm lumped port conserves energy within 5 % (stored = delivered - dissipated; the energy estimate itself is approximate). GPU: CPML runs as extra dispatches of the same shader (per derivative axis, slab-compact psi arrays), ports use a device-side step counter with a per-submit waveform table and an E log. GPU matches the CPU within 1e-4 of the peak with CPML only and with the port only, and within 1e-3 with both (the field left after absorption is small, so the same float noise is a larger share).
- 2026-11-19, **end-to-end checks:** the snapshot -> voxelizer -> solver -> S11 chain reproduces an analytic load: a 50 ohm port across a 2 mm gap with a passive 100 ohm port beside it gives |S11 - 1/3| < 0.002 over 0.3 to 0.6 GHz (S11 = 2 V / Vs - 1, source in series with R = Z0). The KiCAD exporter ran against the W3008 board in pcbnew 10.0.7 (14 copper polygons, 66 vias, stackup 1.53 mm FR4 er 4.5 tan 0.02 between two 35 um copper layers). **Dielectric sub-layer attributes confirmed:** `layer.dielectric.layers[i]` has `epsilon_r`, `loss_tangent`, `thickness` (nm), `material_name`; stackup layer types are named `BSLT_COPPER`, `BSLT_DIELECTRIC` (also silkscreen, solder mask, paste). Pads on a layer come from `get_pad_shapes_as_polygons` per pad (the batch call drops pads that have no shape, so results cannot be matched); filled zones need `refill_zones` in the open board.
- 2026-11-19, **the W3008 chip antenna cannot be simulated from public data.** It is a ceramic loaded PIFA whose radiating structure is inside the body; the datasheet gives the land pattern, the clearance and measured S11 but no internal geometry, so a footprint (pads only) has no antenna in it and the coarse run shows |S11| of about 0 dB. What can be simulated on that board is the feed line, the ground plane and clearance effects, with the chip as a black box. A user whose design has a PCB-trace antenna (inverted-F, meander, patch) is fully modelled. Validation therefore uses a rectangular microstrip patch whose resonance follows the standard cavity-model equations (`plugin/tools/make_patch_snapshot.py`, design 2.45 GHz on 1.6 mm FR4, er 4.5). Results: 1 mm cells on the CPU, dip near 2.4 GHz, -3.6 dB; 0.5 mm cells on the GPU (1.1 M cells, 23 392 steps, 34 s, 766 Mcells/s with CPML, port and a host read every 16 steps), dip at 2.4 GHz, -3.8 dB. So the resonance is about 2 % below the 2.45 GHz design value and stable between the two resolutions; the match is poor (-4 dB) because the probe position was a first guess. Not yet a convergence study: margin and CPML thickness differed between those runs (the CLI now adds the CPML thickness outside the margin).
- Grading is now the blocker for real boards: the 0.3 mm feed gap and 0.15 mm CPWG gaps need cells of 0.1 mm or less near the feed, while the rest of the board can use 0.5 mm or more. A uniform grid fine enough everywhere is tens of millions of cells. The voxelizer widens a port narrower than a cell to one cell and says so. Next: lateral grading (fine cells only near fine features, smooth ratio), then the viewer.

## Sample designs per profile (planned 2026-11-19)
Other profiles need other boards and ranges. Lesson from the W3008: a chip antenna has no published internal geometry, so it cannot be simulated; each sample board must have a **PCB-trace antenna with published dimensions**, with real supporting parts found through Octopart (radio IC or module, RF connector, matching passives). Candidates found (nothing generated yet; every dimension must be checked against the original document):

| Wi-Fi 5 / 6 GHz | printed IFA or patch | (any 5 GHz chip antenna, optional) |

**What a chip-antenna result means** (to be stated in the run summary and the preview whenever the model contains an antenna part): the radiating structure is inside the ceramic body and is not public, so the part is modelled as a dielectric block (body from the footprint courtyard or 3D model, permittivity a user setting with a labelled default) between its real pads. The simulation then covers the feed line, ground plane, clearance and neighbouring parts, and shows how the board changes the match, but it does not reproduce the part's own resonance. Validation for these boards is therefore a before/after comparison (change the ground clearance or feed, see the shift) and a check against the datasheet's own S11 only as a plausibility check, never as a pass/fail. Required exporter work: component bodies (courtyard box, later 3D model) as dielectric blocks, selectable per footprint (docs/ux.md, model selection).
